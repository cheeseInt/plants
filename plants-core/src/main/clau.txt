⏺ Here's a concise breakdown of the plants-core codebase:

  ---
  What's Good

  - Modern stack — Spring Boot 3.2.5 + Java 21, solid foundation
  - Proper layering — Controllers, services, repositories, mappers, DTOs all separated correctly
  - Constructor injection throughout (no field injection)
  - Lombok reducing boilerplate effectively
  - @ConfigurationProperties pattern for external config (FytaProperties)
  - Separate time-series table for measurements — good DB design
  - CareEntryRepository has thoughtful query methods
  - Proper HTTP status codes returned from controllers (201, 204, 404, etc.)
  - Scheduler + PostConstruct for automated data import

  ---
  What Needs Upgrading

  Critical

  1. Hardcoded credentials in application-prod.properties — real email/password in source control. Rotate them immediately and move to env vars.
  2. Hardcoded API token in FytaService.java line 21 — exposed in compiled code.
  3. FytaService login logic is entirely commented out (lines 110–168) — token refresh is broken; the app relies on a hardcoded token.
  4. No global exception handler — exception messages leak to API consumers (PlantController line 151).

  High Priority

  5. Zero tests — no unit, integration, or repository tests at all.
  6. No input validation — no @Valid / @NotNull / @NotBlank anywhere on DTOs or controllers.
  7. PlantEntity is a god object — ~130 fields, mixing too many concerns; needs splitting.
  8. OwnerEntity is completely empty — just annotations, no fields.
  9. Status fields use raw int instead of enums — fragile and unreadable.
  10. Dates stored as Strings in embedded entities — should be LocalDateTime.

  Medium Priority

  11. No database migrations (Flyway/Liquibase) — schema is unversioned.
  12. WebClient uses .block() — defeats reactive benefits, can cause thread starvation.
  13. Hardcoded proxy URL in PlantMapper line 58 — should be in config.
  14. No pagination on list endpoints — will degrade with more data.
  15. Duplicate setBattery() call in PlantImportService lines 108–109 — one is overwritten.
  16. String concatenation for JSON in FytaService line 91 — use ObjectMapper instead.
  17. ~60 lines of commented-out dead code in FytaService.

  Low Priority

  18. No API documentation (Springdoc/OpenAPI/Swagger).
  19. No Spring Security / authentication — all endpoints are open.
  20. No caching for frequently read plants data.

  ---
  Bottom line: The architecture is solid and the tech choices are good. It's a functional MVP, but it has critical security issues (credentials in code) and is missing tests, validation, and proper
  error handling — all of which are essential before treating this as production-grade.

❯ do I need to update my current db .. becuase I already have a lot of entries in it

⏺ Good question to ask before touching anything. Let me break it down by change type:

  ---
  No DB impact at all

  - Input validation (@NotNull, @Valid) — pure Java, no schema change
  - Null safety fixes in PlantImportService — logic only
  - OwnerEntity deletion — it has zero fields, so zero columns exist in the DB. Safe to just remove it.
  - Status int → enum — if stored as @Enumerated(EnumType.ORDINAL) (stores as int), the column type stays INTEGER. No migration needed.

  ---
  DB migration required

  The String → LocalDateTime changes are the only ones that touch the schema. Those 5 columns in the plants table currently hold VARCHAR, and Hibernate needs TIMESTAMP.

  With ddl-auto=update, Hibernate won't auto-convert the column type — it'll either fail silently or throw a mapping error at runtime.

  You'd need this migration before changing the Java types:

  ALTER TABLE plants
    ALTER COLUMN received_data_at         TYPE TIMESTAMP USING received_data_at::TIMESTAMP,
    ALTER COLUMN dismissed_sensor_message_at TYPE TIMESTAMP USING dismissed_sensor_message_at::TIMESTAMP,
    ALTER COLUMN sensor_received_data_at  TYPE TIMESTAMP USING sensor_received_data_at::TIMESTAMP,
    ALTER COLUMN hub_received_data_at     TYPE TIMESTAMP USING hub_received_data_at::TIMESTAMP,
    ALTER COLUMN hub_reached_hub_at       TYPE TIMESTAMP USING hub_reached_hub_at::TIMESTAMP;

  This only works cleanly if the stored strings are consistently formatted as yyyy-MM-dd HH:mm:ss. If any rows have nulls or malformed values in those columns, the ::TIMESTAMP cast will throw.
